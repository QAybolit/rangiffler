# Review test resource ownership

A resource is anything a test gets and must give back: DB rows, Page, BrowserContext. For each one find the owner, when it is acquired, where it is kept and when it is released.

## Rules

1. **The owner is the decorator tree.** The Store holds only the root `UserFixture` from `UserRequest.fixture()`, and `UserExtension.afterEach` closes it. Each decorator owns its `origin` and its own partner fixtures. Extension fields, statics and `ThreadLocal` own nothing, except the pool in rule 9.
2. **Closable after any failed step.** `create()` is not atomic (account, profile, partners, friendship). Either register in the Store before `create()` ends, or roll back inside `create()` as `BaseUserFixture` and the decorators do; `close()` must work after a failure at any step.
3. **Symmetry of create and close.** A decorator deletes exactly what it created, by username, in reverse order: own partners, then `origin`. Partner users and their friendships are created and closed through `Partners`, so check that a decorator does not bypass it. Steps are independent and the first failure is kept with the rest suppressed. No broad `DELETE` or `TRUNCATE`.
4. **A new precondition is a new decorator.** Compose it in `UserRequest.fixture()`; no flag in a fixture and no branch in `UserExtension`. The extension knows only `UserRequest` and `UserFixture`.
5. **One `@User`, one `TestUser` parameter.** The Store key is the test's unique id, not the parameter index, and only the first `@User` parameter is read. Related users live inside `TestUser` and the fixture tree, not in extra parameters. An annotation in a place the extension does not support (a second parameter, a lifecycle method) must fail with a clear error before any resource is acquired, never silently share or skip.
6. **Browser resources belong to `@UsePlaywright`.** `BaseWebTest` only declares it with `PlaywrightOptions` and keeps the injected `Page`; tests and extensions never create or close Playwright, Browser, BrowserContext or Page.
7. **Layers.** `jupiter` has no SQL and no locators; `data` has no JUnit; SQL lives only in `data/db`, which does not depend on `data`; `test` has no locators and no SQL.
8. **Evidence.** Back every finding with a probe in `jupiter/probe/UserExtensionTest`, `UsersQueueExtensionTest` or `SuiteExtensionTest` (EngineTestKit, `userExists` from `data/db`, sample classes with `StoreProbe`) or a concrete code line. Propose no change without a cause found. A probe must prove it ran: assert the number of failed or passed sample tests, and check a failure by its message, not only by its class. Never hardcode the pool size in a probe.
9. **Borrowed resources.** A user taken from the static pool (`StaticUserFixture`) is borrowed, not created: `close()` gives back only what this fixture took, exactly once, and a stale `close()` must not touch a user another test now holds. Waiting is bounded by a timeout and fails with a clear error. Nothing is deleted from the DB, and the user's state is not reset, so a test must not change a pooled user.
10. **Class-level extensions are declared on a class or a static field only.** An extension that implements a class-level callback (`BeforeAllCallback`, `AfterAllCallback`) is registered declaratively only with `@ExtendWith` over the test class (a meta-annotation, a superclass or an interface included) or over a `static` field; a `SuiteExtension` is the exception and is registered through `ServiceLoader` (rule 13). Any other place is a defect: on a test method, a lifecycle method, a parameter, a constructor parameter or a non-static field the extension is registered after the class has started, so `beforeAll` and `afterAll` never run and the resource they own is neither acquired nor released. Report it with the file and line, and either move the annotation to the class or split the extension so that the class-level part is registered over the class.
11. **An extension is safe for any test in the project.** It makes no assumption about where it is registered: over a test method, over a class (so every test of it, nested classes included) or globally through auto-detection. Before acquiring any resource or creating test data, it checks the signature of the current test: that `getTestMethod()` is present (a class-level callback has none), and that the method has the parameter or annotation the extension serves. For a test without them it does nothing and leaves no state in the Store, and its `afterEach` releases only what its own `beforeEach` acquired. Look for `getRequiredTestMethod()` without a check, a resource created for every test of the class, a parameter read by index without a type check, and a `supportsParameter` that accepts a parameter of a test it does not serve. Back the finding with a probe: a sample class with a test that has no annotation and a class-level registration, which must pass and acquire nothing.
12. **Register extensions declaratively.** Use `@ExtendWith` (directly, on a composed annotation, or over a static field for a class-level extension). A programmatic `@RegisterExtension` field is allowed only when the extension must be configured through a constructor or a builder, for example with a timeout or a port; such a field is `static` for a class-level extension, as rule 10 requires. Report a `@RegisterExtension` of an extension that has a no-argument constructor and takes nothing from the test. Auto-detection through `ServiceLoader` is enabled in `junit-platform.properties`: an extension listed in `META-INF/services/org.junit.jupiter.api.extension.Extension` is registered for every test in the project, so it must satisfy rule 11, and report an extension listed there that serves only some tests.
13. **Suite extensions are registered globally through `ServiceLoader`.** Every implementation of `SuiteExtension` (an extension of the whole test run) is listed in `src/test/resources/META-INF/services/org.junit.jupiter.api.extension.Extension`, and `junit.jupiter.extensions.autodetection.enabled=true` stays in `junit-platform.properties`. Report an implementation that is registered by `@ExtendWith` or `@RegisterExtension` in a test class, because it would then act only for the tests that name it, and one that is missing from the services file, because it never acts. Sample classes inside `SuiteExtensionTest`, which probe the interface through EngineTestKit, are the only exception. Check the services file for a class that no longer exists or is listed twice, and keep the listed order as the order of the starts: `StandReadinessExtension` stays above `MigrationCheckExtension`, which `ServicesOrderTest` checks, and any other suite extension must not depend on the order. A suite extension that serves only some tests overrides `appliesTo` instead of ignoring the other tests inside `beforeSuite`.

## Answer format

- For each resource: owner, acquisition, storage, release (borrowed or created).
- For each finding: file and line, failure scenario, how to reproduce.
- Three lists: confirmed by a run, from reading the code, not checked.
- If there are no defects, say so and list the limits of the solution.
